DIAGNÓSTICO — por qué hoy hay proveedores "con perfil completo" sin fotos
===========================================================================
Hay DOS cosas distintas que se llaman "perfil completo" en el sistema y no están conectadas entre sí:

1. `users.perfil_completo` (boolean) — se marca en `CompletarPerfilController::store()` cuando el
   usuario llena un formulario GENÉRICO (teléfono, CURP, RFC personal, municipio, nombre de empresa,
   cámara/asociación). Es el mismo para compradores y proveedores, y es el único que usa hoy el
   middleware `EnsureProfileComplete` para bloquear el acceso a la plataforma.
2. El perfil DE NEGOCIO del proveedor (logo, productos, descripción, RFC del negocio, etc.) se llena
   en un formulario totalmente distinto — el modal "Editar perfil de negocio" dentro de
   `resources/js/Pages/Restaurantero/Panel.vue` (variable `formPerfil`, función `submitPerfil()`),
   que envía a `ProveedorPerfilController::store()`. Ese formulario NO marca ningún campo de
   "completo" — solo guarda lo que se le envíe, y casi todos sus campos son `nullable`.

Por eso un proveedor puede tener `users.perfil_completo = true` (llenó el formulario genérico) sin
haber subido nunca logo ni productos — exactamente el problema reportado.

Dato interesante: `Panel.vue` YA tiene una barra de progreso informal para esto
(`perfilPorcentaje` y `perfilCamposFaltantes`, líneas 182-207), pero es solo cosmética — no bloquea
nada ni se usa en el badge del admin ni en el directorio público. Este prompt la actualiza y, sobre
todo, crea un criterio real y guardado en base de datos para "perfil completo de negocio".

IMPORTANTE — esto ACTUALIZA el prompt anterior (`PROMPT_PERFIL_COMPLETO_PROVEEDORES.txt`, si ya se
aplicó): ese prompt usaba `users.perfil_completo` tanto para el badge de
Admin > Restauranteros > Show como para el filtro de la sección "Explora los proveedores de la
plataforma". Con este cambio, AMBOS deben usar el nuevo criterio de `restauranteros.perfil_completo`
(ver Punto 1) en vez de `users.perfil_completo`. Las instrucciones de abajo ya indican el código
final correcto — si ese prompt anterior no se ha aplicado todavía, aplica directamente esta versión.

Dos campos existentes que NO se incluyen como requisito de "perfil completo" y por qué:
- `categoria` (la categoría/sector mostrada en los filtros) solo la puede asignar el ADMIN
  (`RestauranteroAdminController::updateCategoria()`), el proveedor no la edita en su propio
  formulario. Si se exigiera para "perfil completo", un proveedor podría llenar todo correctamente y
  seguir sin poder completarlo hasta que el admin le asigne categoría — un callejón sin salida
  confuso. Por eso no se incluye. Si Diego prefiere que sí cuente, hay que avisar explícitamente
  porque cambia el flujo (el admin tendría que asignar categoría ANTES de que el proveedor pueda
  quedar completo).
- `direccion` ya existe como variable en `formPerfil` y se envía al backend (línea 108 y 136 de
  Panel.vue), pero NO tiene ningún `<input>` visible en el formulario actual — es un campo "fantasma"
  que hoy nunca se puede llenar desde la interfaz. Por la misma razón que `categoria`, no se incluye
  como requisito. Si se quiere usar, primero hay que agregarle un input real al formulario (cambio
  menor, no incluido aquí para no ampliar el alcance).

```php
protected static function booted(): void
{
    static::saving(function (Restaurantero $r) {
        $r->perfil_completo = $r->calcularPerfilCompleto();
    });
}

public function calcularPerfilCompleto(): bool
{
    $infoBasica = filled($this->nombre_restaurante)
        && filled($this->descripcion)
        && filled($this->telefono)
        && filled($this->municipio);

    $tieneLogo = filled($this->logo_path);

    $tieneProducto = !empty($this->productos_top)
        && collect($this->productos_top)->contains(fn ($p) => filled($p['nombre'] ?? ($p ?? null)));

    $facturaOk = !$this->factura || (filled($this->rfc) && filled($this->regimen_fiscal));

    $creditoOk = !$this->acepta_credito || (
        filled($this->credito_monto_maximo)
        && filled($this->credito_tiempo_cantidad)
        && filled($this->credito_tiempo_unidad)
    );

    return $infoBasica && $tieneLogo && $tieneProducto && $facturaOk && $creditoOk;
}
```
Al usar un evento `saving`, `perfil_completo` se recalcula automáticamente cada vez que se guarda el
modelo desde CUALQUIER controlador (el del proveedor, el del admin, aprobación, etc.) — no hay que
recordar llamarlo manualmente en varios lugares.

5. Verificación:
   a. Abrir el perfil de un proveedor que hoy NO tenga logo ni productos → debe verse "Perfil
      incompleto" en el admin, y NO debe aparecer en "Explora los proveedores de la plataforma" en
      la página pública (aunque su `users.perfil_completo` siga en true).
   b. Como ese proveedor, entrar a su Panel y llenar logo + al menos 1 producto + descripción +
      teléfono + municipio + responder crédito/contraentrega/factura → al guardar, debe pasar a
      "Perfil completo" automáticamente (sin tocar nada más) y aparecer en el directorio público.
   c. Marcar "Sí" en "¿Emites factura?" sin llenar RFC o régimen fiscal → debe bloquear el guardado
      con error de validación.
   d. Marcar "Sí" en "¿Aceptas crédito?" sin llenar monto o plazo → debe bloquear el guardado.
   e. Guardar con factura = No y crédito = No → debe guardar sin pedir esos campos, y el perfil debe
      poder quedar completo igual si lo demás está lleno.
   f. Revisar el perfil público de un proveedor con crédito/contraentrega/factura llenos → deben
      verse los badges de "Condiciones comerciales", y el RFC del negocio NO debe aparecer en el
      HTML de esa página (sigue oculto).
   g. Confirmar que el RFC personal del usuario (`users.rfc`, de Completar Perfil) y el RFC del
      negocio (`restauranteros.rfc`) son independientes y no se pisan entre sí.
