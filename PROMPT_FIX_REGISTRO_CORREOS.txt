CAMBIO 2 — app/Actions/Fortify/CreateNewUser.php
─────────────────────────────────────────────────────────────

CAUSA DEL 500: Fortify dispara el evento `Registered` tras crear al usuario.
El listener `SendEmailVerificationNotification` llama a SMTP en producción.
Si SMTP falla → excepción sin catch → HTTP 500.

LA FIX: agregar `'email_verified_at' => now()` al User::create(). Esto hace
que `$user->hasVerifiedEmail()` retorne true, y el listener omite el envío
del correo de verificación. Sin llamada SMTP → sin posibilidad de 500.

Es consistente con el flujo de Google OAuth (SocialAuthController.php línea 46
ya hace exactamente esto).

En el método create(), localiza el bloque User::create([...]) y agrega la línea:

        $user = User::create([
            'name'             => $input['name'],
            'email'            => $input['email'],
            'password'         => Hash::make($input['password']),
            'telefono'         => $input['telefono'] ?? null,
            'curp'             => $input['curp'] ?? null,
            'active_role'      => 'comprador',
            'acepta_aviso_at'  => now(),
            'email_verified_at'=> now(),   // ← NUEVO: auto-verifica igual que Google OAuth
        ]);

CAMBIO 3 — app/Models/User.php
─────────────────────────────────────────────────────────────

Agregar este método al modelo para que el botón "Reenviar correo de
verificación" en VerifyEmail.vue nunca cause un 500 aunque SMTP falle.
Fortify llama a este método tanto en el registro como en el reenvío manual.

Dentro de la clase User, justo antes del cierre de la clase, agrega:

    /**
     * Envuelve el envío del correo de verificación en try/catch.
     * Si SMTP falla, registra el error pero no lanza excepción al usuario.
     */
    public function sendEmailVerificationNotification(): void
    {
        try {
            parent::sendEmailVerificationNotification();
        } catch (\Exception $e) {
            \Log::error('Error al enviar correo de verificación a ' . $this->email . ': ' . $e->getMessage());
        }
    }

NOTA: con el CAMBIO 2 activo, los usuarios nuevos ya tienen email_verified_at
establecido, por lo que el listener nunca llamará a este método en el registro.
Este override es solo una red de seguridad para el botón de reenvío manual.

CAMBIO 4 — Error 419 (CSRF / sesión expirada)
─────────────────────────────────────────────────────────────

El error 419 en el formulario /register ocurre cuando:
a) El usuario dejó la página abierta mucho tiempo y la sesión expiró.
b) La variable APP_URL en .env de producción no coincide con la URL real
   (ej: APP_URL=http://... pero el sitio corre en https://...).

Inertia v2 (que usa este proyecto) ya maneja el 419 automáticamente:
recarga la página y reintenta la acción. No se necesita código extra.

VERIFICAR EN .env DE PRODUCCIÓN (en el servidor):

    APP_URL=https://impulsate.iyemyucatan.com   ← debe ser https si el sitio es https
    SESSION_SECURE_COOKIE=true                  ← activar si el sitio es https
    SESSION_DOMAIN=impulsate.iyemyucatan.com    ← sin punto inicial para un solo dominio

Si SESSION_SECURE_COOKIE era false y el sitio corre en https, la cookie XSRF
no se envía y cada request da 419. Cambiar a true soluciona el problema.

Después de editar .env:
    php artisan config:clear
    php artisan cache:clear

CAMBIO 5 — Flujo de verificación de correo (VerifyEmail.vue)
─────────────────────────────────────────────────────────────

Con el CAMBIO 2, los usuarios que se registran por el formulario ya tienen
`email_verified_at` establecido. Nunca verán la pantalla VerifyEmail.vue.
La página permanece disponible para usuarios creados antes de este fix
(con email_verified_at null) que quieran reenviar el correo.

El CAMBIO 3 garantiza que si hacen clic en "Reenviar correo de verificación"
y el SMTP falla, no ven un error 500 — ven la página normalmente.

No se necesita modificar VerifyEmail.vue.
