CAMBIO 1 — Encolar los 13 Mailables que faltan
13 archivos, 2 líneas cada uno
─────────────────────────────────────────────────────────────

Solo PlantillaCorreoMail implementa ShouldQueue. Los otros 13 envían de
forma síncrona dentro del request: cada Mail::to()->send() bloquea 1-3
segundos en el handshake SMTP, y si el SMTP cae, el usuario recibe un 500
DESPUÉS de que la acción ya se aplicó en la base de datos.

Esa es la causa raíz del parche 2026_08_17_120000_verify_existing_users_again:
el registro fallaba con 500 porque el correo de verificación reventaba.

**Es la corrección con mejor retorno de toda la auditoría**: Mail::to()->send()
sobre un Mailable encolable encola automáticamente, así que estas 26 líneas
arreglan ~25 puntos de envío repartidos por todo el proyecto, sin tocar
ningún controlador.

LOS 13 ARCHIVOS:

    app/Mail/CitaAceptada.php
    app/Mail/CitaAgendada.php
    app/Mail/CitaCancelada.php
    app/Mail/CitaConfirmada.php
    app/Mail/CitaReagendada.php
    app/Mail/CitaRechazada.php

EN CADA UNO, dos cambios idénticos.

1) BUSCA la línea:

    use Illuminate\Mail\Mailable;

   AÑADE JUSTO ANTES:

   (queda en orden alfabético, igual que en PlantillaCorreoMail)

2) BUSCA la declaración de la clase:

    class NOMBRE extends Mailable

   REEMPLÁZALA POR:

   donde NOMBRE es el de cada archivo. Por ejemplo:

    class CitaAceptada extends Mailable implements ShouldQueue

⚠ NO toques el `use Queueable, SerializesModels;` de dentro de la clase:
   ya está en los 13 y es justo lo que hace falta.

⚠ NO toques PlantillaCorreoMail: ya lo tiene.

VERIFICACIÓN:

(no debe devolver ningún archivo)

PRUEBAS IMPRESCINDIBLES DESPUÉS:
  □ El worker está corriendo (Fase 2.5 P4)
  □ Agendar una cita: el correo llega en menos de 5 minutos
  □ SELECT COUNT(*) FROM jobs baja a 0 después de que corra el worker

CAMBIO 3 — Ejecución remota de código en la subida de logo
app/Http/Controllers/Admin/RestauranteroAdminController.php + .htaccess
─────────────────────────────────────────────────────────────

La validación es `mimes:jpg,jpeg,png,webp`, que Laravel comprueba contra la
extensión ADIVINADA DEL CONTENIDO. Pero el nombre del archivo se construye
con getClientOriginalExtension(), que es la extensión QUE ENVÍA EL CLIENTE.

Un JPEG real renombrado a evil.php pasa la validación y se guarda como .php
dentro de storage/app/public/logos/. Y el .htaccess sirve /storage/ sin
impedir la ejecución de PHP.

Requiere rol admin, así que es escalada de admin a RCE, no acceso anónimo.
Pero con cero Policies y varios admins, la superficie es real.

3.1 — BUSCA (línea ~249-263):

        if ($request->hasFile('logo')) {
            $file     = $request->file('logo');
            $filename = 'logo_' . $restaurantero->id . '_' . uniqid() . '.' . $file->getClientOriginalExtension();
            $dir      = storage_path('app/public/logos');

            if (!is_dir($dir)) {
                mkdir($dir, 0755, true);
            }

            if ($restaurantero->logo_path && str_starts_with($restaurantero->logo_path, 'logos/logo_')) {
                @unlink(storage_path('app/public/' . $restaurantero->logo_path));
            }

            $file->move($dir, $filename);
            $data['logo_path'] = 'logos/' . $filename;
        }

REEMPLÁZALO POR:

        if ($request->hasFile('logo')) {
            $file = $request->file('logo');

            // extension() adivina la extension a partir del CONTENIDO real.
            // getClientOriginalExtension() devuelve lo que mande el cliente:
            // un JPEG renombrado a .php pasaba la validacion de mimes y se
            // guardaba como .php dentro de storage, que el servidor sirve.
            $extension = strtolower($file->extension());

            if (!in_array($extension, ['jpg', 'jpeg', 'png', 'webp'], true)) {
                return back()->withErrors(['logo' => 'El archivo debe ser una imagen JPG, PNG o WEBP.']);
            }

            $filename = 'logo_' . $restaurantero->id . '_' . uniqid() . '.' . $extension;
            $dir      = storage_path('app/public/logos');

            if (!is_dir($dir)) {
                mkdir($dir, 0755, true);
            }

            if ($restaurantero->logo_path && str_starts_with($restaurantero->logo_path, 'logos/logo_')) {
                @unlink(storage_path('app/public/' . $restaurantero->logo_path));
            }

            $file->move($dir, $filename);
            $data['logo_path'] = 'logos/' . $filename;
        }

3.2 — DEFENSA EN PROFUNDIDAD (obligatoria, no opcional)

Aunque el punto anterior cierre este caso concreto, nada impide que un futuro
punto de subida cometa el mismo error. Bloquea la ejecución de PHP bajo
/storage/ de una vez.

OPCIÓN A (preferida) — un .htaccess dentro de la carpeta de subidas.
CREA storage/app/public/.htaccess con:

    # Nada de lo que suben los usuarios debe ejecutarse jamas.
    php_flag engine off
    <FilesMatch "\.(php|phtml|php[0-9]|phar|pl|py|cgi|sh|htaccess)$">
        Require all denied
    </FilesMatch>

⚠ php_flag solo funciona con mod_php. Si Hostinger usa PHP-FPM lo ignorará
   silenciosamente — por eso el FilesMatch va también, que sí funciona siempre.

OPCIÓN B — en el .htaccess de la raíz, junto al blindaje que ya tienes:

    # Nada ejecutable bajo /storage/ (son archivos subidos por usuarios)
    RewriteRule ^storage/.*\.(php|phtml|php[0-9]|phar|pl|py|cgi|sh)$ - [F,L]

   ⚠ Esta regla debe ir ANTES de la línea que reescribe /storage/ hacia
      public/storage/, o no se llegará a evaluar.

VERIFICACIÓN (hazla de verdad, no la des por buena):

  1. Crea un archivo de prueba en local:
     echo '<?php echo "EJECUTADO"; ?>' > /tmp/prueba.php
  2. Renómbralo a prueba.jpg, súbelo como logo desde el panel admin.
     → debe ser rechazado por la validación nueva (no es una imagen real)
  3. Toma un JPG real, renómbralo a real.php, súbelo.
     → debe guardarse como .jpg, no como .php
  4. Si en el servidor quedó algún .php de intentos anteriores:
     find storage/app/public -name "*.php" -o -name "*.phtml" | head

CAMBIO 11 — Hacer idempotente la migración de tv_token
database/migrations/2026_08_27_120000_add_tv_token_to_eventos_table.php
─────────────────────────────────────────────────────────────

Primero el DDL (que en MySQL hace commit implícito) y después un bucle que
genera el token de cada evento. Si el bucle muere a la mitad, la columna ya
existe, algunos eventos tienen token y otros no, y la fila NO llegó a
escribirse en la tabla `migrations`.

Resultado: el siguiente migrate falla con "Duplicate column name 'tv_token'"
y bloquea el despliegue completo.

⚠ SI YA LA CORRISTE SIN PROBLEMAS, este cambio es preventivo: protege contra
   un re-run en otro entorno (staging, la máquina de otro desarrollador).

BUSCA:

    public function up(): void
    {
        Schema::table('eventos', function (Blueprint $table) {
            $table->string('tv_token', 64)->nullable()->unique()->after('activa');
        });

        // Generar uno para cada evento existente
        foreach (DB::table('eventos')->pluck('id') as $id) {
            DB::table('eventos')->where('id', $id)->update(['tv_token' => Str::random(48)]);
        }
    }

REEMPLAZA POR:

    public function up(): void
    {
        // El DDL hace commit implicito en MySQL: si el backfill muere despues,
        // la columna existe pero la migracion no queda registrada, y el
        // siguiente migrate falla con "Duplicate column name".
        if (!Schema::hasColumn('eventos', 'tv_token')) {
            Schema::table('eventos', function (Blueprint $table) {
                $table->string('tv_token', 64)->nullable()->unique()->after('activa');
            });
        }

        // Solo los que aun no tienen token: reanudable sin efectos secundarios.
        foreach (DB::table('eventos')->whereNull('tv_token')->pluck('id') as $id) {
            DB::table('eventos')->where('id', $id)->update(['tv_token' => Str::random(48)]);
        }
    }
