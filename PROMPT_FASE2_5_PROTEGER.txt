PASO 2 — Respaldo del bloqueo de directorios FUERA de mod_rewrite

Hoy .git/ solo está bloqueado por un RewriteRule que vive DENTRO de
<IfModule mod_rewrite.c>. Si mod_rewrite se desactivara, el bloqueo
desaparece y el FilesMatch no lo respalda: el historial completo de git
—con el secreto de P2 dentro— quedaría descargable. Falla en abierto.

AÑADE en .htaccess, justo después del bloque <Files "robots.txt">:

    # Respaldo del bloqueo de directorios, INDEPENDIENTE de mod_rewrite.
    # Si mod_rewrite se desactivara, el RewriteRule de abajo dejaria de
    # proteger .git/ y el historial completo quedaria descargable.
    RedirectMatch 404 ^/(\.git|\.github|vendor|database|bootstrap|config|app|resources|routes|tests|node_modules)(/|$)

⚠ NO incluyas "storage" en esa lista. Ya lo tienes documentado en tu propio
   .htaccess y es correcto: la regla de arriba reescribe /storage/* hacia
   public/storage/* y bloquearlo rompería las imágenes.

P4 — VERIFICAR EL CRON Y LA COLA EN PRODUCCIÓN
─────────────────────────────────────────────────────────────

Esta es, con diferencia, la causa más probable de "los correos no llegan".

Con QUEUE_CONNECTION=database y sin worker corriendo, cada ->queue() inserta
una fila en la tabla `jobs`, le dice al admin "enviado", y el correo no sale
NUNCA. Nada en el repositorio instala ese cron: DEPLOY.md lo deja como paso
manual y ninguno de los 71 deploy_*.py lo configura.

PASO 1 — Mirar qué hay:

    ssh -p 65002 u489236361@195.35.38.222
    crontab -l

Deberías ver algo como:

    * * * * * cd /home/.../public_html && php artisan schedule:run >> /dev/null 2>&1
    */5 * * * * cd /home/.../public_html && php artisan queue:work --stop-when-empty >> /dev/null 2>&1

PASO 2 — Mirar la cola:

    php artisan tinker
    >>> DB::table('jobs')->count();
    >>> DB::table('failed_jobs')->count();
    >>> DB::table('jobs')->orderBy('id')->first();

INTERPRETACIÓN:
  jobs = 0            → o no hay trabajos, o el worker los está procesando. Bien.
  jobs > 0 y creciendo → EL WORKER NO ESTÁ CORRIENDO. Ahí están tus correos.
  failed_jobs > 0     → revisa el campo `exception` de esas filas.

PASO 3 — Si el cron no está, ponlo (panel de Hostinger → Cron Jobs):

    * * * * *    cd /home/u489236361/domains/impulsate.iyemyucatan.com/public_html && php artisan schedule:run >> /dev/null 2>&1
    */5 * * * *  cd /home/u489236361/domains/impulsate.iyemyucatan.com/public_html && php artisan queue:work --stop-when-empty --tries=3 --max-time=280 >> ~/logs/queue.log 2>&1

PASO 4 — Si Hostinger no permite workers o prefieres no depender del cron:

En el .env de producción cambia:

Con eso los correos se envían dentro del request (lento, pero salen).
Es peor para el rendimiento pero mejor que no enviarlos. La Fase 3 asume
que la cola FUNCIONA, así que decide esto antes de aplicarla.

PASO 5 — Vaciar la cola atascada, si la hay:

P6 — ARREGLAR LA MIGRACIÓN DE DOCUMENTOS ANTES DE CORRERLA
─────────────────────────────────────────────────────────────

⚠ ESTE ES EL ÚNICO PUNTO DE ESTE DOCUMENTO CON RIESGO DE PÉRDIDA DE DATOS.

Estado actual de
database/migrations/2026_08_27_100000_mover_documentos_a_disco_privado.php:

    Storage::disk('local')->put($rutaNueva, Storage::disk('public')->get($rutaVieja));
    Storage::disk('public')->delete($rutaVieja);      ← borra pase lo que pase

    ...y el UPDATE de la BD ocurre DESPUÉS, al final del usuario.

Y config/filesystems.php declara 'throw' => false en ambos discos: si el
put() falla por permisos o disco lleno, **devuelve false en silencio y el
original se borra igual**.

Dos formas de perder INE y CSF de forma irrecuperable:
  a) Un permiso mal puesto en storage/app/private → borrado masivo silencioso.
  b) El proceso muere entre el delete y el UPDATE → archivo con nombre
     aleatorio en privado y la BD apuntando a una ruta ya borrada.

────────────────────────────────
PRIMERO: ¿ya la corriste?
────────────────────────────────

    php artisan migrate:status | grep mover_documentos

  • Si dice "Pending" en producción → NO la corras todavía. Aplica el arreglo
    de abajo primero.

  • Si dice "Ran" en producción → verifica que no se perdió nada ANTES de
    hacer nada más:

        php artisan tinker
        >>> $rotos = App\Models\User::whereNotNull('ine_path')->get()
        ...     ->filter(fn($u) => !Storage::disk('local')->exists($u->ine_path));
        >>> $rotos->count();
        >>> $rotos->pluck('id', 'email');

        >>> $rotosCsf = App\Models\User::whereNotNull('csf_path')->get()
        ...     ->filter(fn($u) => !Storage::disk('local')->exists($u->csf_path));
        >>> $rotosCsf->count();

    Si ambos cuentan 0, tuviste suerte y no hay nada que lamentar.
    Si alguno es > 0, esos usuarios perdieron su documento: hay que pedírselo
    de nuevo. Busca también huérfanos en storage/app/private/documentos que
    no correspondan a ninguna ruta en BD.

────────────────────────────────
EL ARREGLO
────────────────────────────────

BUSCA en la migración este bloque:

                $extension = pathinfo($rutaVieja, PATHINFO_EXTENSION) ?: 'pdf';
                $rutaNueva = "documentos/{$u->id}/{$tipo}_" . Str::random(40) . ".{$extension}";

                Storage::disk('local')->put($rutaNueva, Storage::disk('public')->get($rutaVieja));
                Storage::disk('public')->delete($rutaVieja);

                $cambios[$tipo . '_path'] = $rutaNueva;
                $movidos++;

REEMPLÁZALO POR:

                $extension = pathinfo($rutaVieja, PATHINFO_EXTENSION) ?: 'pdf';
                $rutaNueva = "documentos/{$u->id}/{$tipo}_" . Str::random(40) . ".{$extension}";

                // Los discos tienen 'throw' => false: get() devuelve null y put()
                // devuelve false en silencio si fallan. Hay que comprobarlos, o el
                // delete de abajo borraria el original sin tener copia.
                $contenido = Storage::disk('public')->get($rutaVieja);

                if ($contenido === null) {
                    $faltantes++;
                    Log::error("[mover_documentos] No se pudo leer {$rutaVieja} (user {$u->id}). NO se borra el original.");
                    continue;
                }

                if (Storage::disk('local')->put($rutaNueva, $contenido) === false) {
                    $faltantes++;
                    Log::error("[mover_documentos] Fallo al escribir {$rutaNueva} (user {$u->id}). Revisa permisos de storage/app/private. NO se borra el original.");
                    continue;
                }

                // Verificar que la copia existe y no quedo vacia
                if (!Storage::disk('local')->exists($rutaNueva)
                    || Storage::disk('local')->size($rutaNueva) !== strlen($contenido)) {
                    $faltantes++;
                    Log::error("[mover_documentos] La copia de {$rutaNueva} no coincide en tamano (user {$u->id}). NO se borra el original.");
                    continue;
                }

                // Escribir la BD ANTES de borrar el original: si el proceso muere
                // aqui, el documento sigue existiendo en publico y la ruta vieja
                // sigue siendo valida. La guarda de idempotencia lo retomara.
                DB::table('users')->where('id', $u->id)->update([$tipo . '_path' => $rutaNueva]);

                Storage::disk('public')->delete($rutaVieja);

                $movidos++;

Y MÁS ABAJO, BUSCA:

            if ($cambios) {
                DB::table('users')->where('id', $u->id)->update($cambios);
            }

REEMPLÁZALO POR:

            // El UPDATE ya se hace campo por campo arriba, en cuanto la copia
            // esta verificada. Aqui no queda nada que escribir.

⚠ La variable $cambios queda sin uso. Puedes borrar también su declaración
   ($cambios = []; unas líneas más arriba) o dejarla, es inocuo.
