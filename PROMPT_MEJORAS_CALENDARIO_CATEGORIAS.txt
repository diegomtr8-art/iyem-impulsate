PASO 2E — CONTROLLER SuperAdmin: CategoriasController
------------------------------------------------------
Crear: app/Http/Controllers/Admin/SuperAdmin/CategoriasController.php

    <?php
    namespace App\Http\Controllers\Admin\SuperAdmin;
    use App\Http\Controllers\Controller;
    use App\Models\Categoria;
    use Illuminate\Http\Request;
    use Inertia\Inertia;

    class CategoriasController extends Controller
    {
        public function index()
        {
            return Inertia::render('Admin/SuperAdmin/Categorias/Index', [
                'categorias' => Categoria::orderBy('orden')->get(),
            ]);
        }

        public function store(Request $request)
        {
            $request->validate(['nombre' => 'required|string|max:100|unique:categorias,nombre']);
            $maxOrden = Categoria::max('orden') ?? 0;
            Categoria::create(['nombre' => $request->nombre, 'orden' => $maxOrden + 1, 'activo' => true]);
            return back()->with('success', 'Categoría agregada.');
        }

        public function update(Request $request, Categoria $categoria)
        {
            $request->validate(['nombre' => 'required|string|max:100|unique:categorias,nombre,' . $categoria->id]);
            $categoria->update(['nombre' => $request->nombre]);
            return back()->with('success', 'Categoría actualizada.');
        }

        public function toggle(Categoria $categoria)
        {
            $categoria->update(['activo' => !$categoria->activo]);
            return back()->with('success', $categoria->activo ? 'Categoría activada.' : 'Categoría desactivada.');
        }

        public function destroy(Categoria $categoria)
        {
            // Solo borrar si no está en uso
            $enUso = \App\Models\Restaurantero::where('categoria', $categoria->nombre)->exists();
            if ($enUso) {
                return back()->withErrors(['error' => 'No se puede eliminar: hay proveedores con esta categoría.']);
            }
            $categoria->delete();
            return back()->with('success', 'Categoría eliminada.');
        }

        public function reordenar(Request $request)
        {
            // Recibe array de IDs en el nuevo orden
            $request->validate(['ids' => 'required|array']);
            foreach ($request->ids as $i => $id) {
                Categoria::where('id', $id)->update(['orden' => $i]);
            }
            return back()->with('success', 'Orden actualizado.');
        }
    }

LÍMITE DE CORREOS — NOTA IMPORTANTE
-------------------------------------
Gmail SMTP (impulsate@iyemyucatan.com con App Password) tiene un límite
de 500 correos por día. Si el envío masivo supera ese número en un solo
día, los correos adicionales rebotarán silenciosamente o serán rechazados.

Para envíos grandes (más de 200 correos), se recomienda:
1. Configurar Laravel Queue con un rate limiter (1 correo cada 2 segundos)
2. O dividir el envío en grupos de 200 por día

Por ahora el sistema no tiene límite propio — el throttle lo impone Gmail.
Para mitigar, en el controller enviar() agregar un sleep entre envíos:
    Mail::to($user->email)->queue(new PlantillaCorreoMail(...));
    // Las colas ya ayudan a espaciar. Para más control, ver queue:work --sleep=2

CAMBIO 7 — DEBUG: INFORMACIÓN DE PROVEEDORES NO GUARDA
====================================================================

CONTEXTO
--------
Algunos proveedores reportan que su información no se guarda. No es
todos, solo algunos. Hay varias causas posibles identificadas:

CAUSA A: Campo entrega_domicilio requerido en validación
--------------------------------------------------------
En ProveedorPerfilController.php, línea 74:
    'entrega_domicilio' => ['required', 'boolean'],

Este campo está como REQUERIDO (no nullable). Si el proveedor tiene
una versión anterior del formulario cargada en caché del navegador
o si el campo no llega en el FormData, Laravel retorna 422 pero
Inertia puede no mostrar el error claramente.

FIX: Cambiar a nullable y poner valor por defecto:
    'entrega_domicilio' => ['nullable', 'boolean'],

Y en el bloque de procesamiento, cambiar:
    $data['entrega_domicilio'] = filter_var(
        $request->entrega_domicilio,
        FILTER_VALIDATE_BOOLEAN,
        FILTER_NULL_ON_FAILURE
    );
    // Si viene null (no se envió), poner false por defecto:
    if (is_null($data['entrega_domicilio'])) {
        $data['entrega_domicilio'] = false;
    }

CAUSA B: Validación de sitio_web con URL inválida
--------------------------------------------------
La regla 'url' de Laravel requiere que el URL incluya protocolo
(https://). Si el usuario escribe "www.ejemplo.com" sin https://,
la validación falla silenciosamente en algunos navegadores.

FIX en ProveedorPerfilController.php:
    'sitio_web' => ['nullable', 'string', 'max:200'],

Y en el controller, antes de guardar, normalizar la URL:
    if (!empty($data['sitio_web']) && !preg_match('/^https?:\/\//', $data['sitio_web'])) {
        $data['sitio_web'] = 'https://' . $data['sitio_web'];
    }

CAUSA C: Timeout en subida de fotos grandes
--------------------------------------------
El campo foto tiene validación 'max:4096' (4MB). Si el servidor tiene
un php.ini con upload_max_filesize o post_max_size menor, la petición
falla a nivel de PHP antes de llegar al controlador, y el error no
se muestra claramente.

FIX: Verificar en php.ini de producción:
    upload_max_filesize = 5M
    post_max_size = 10M

También en el controller, agregar manejo explícito:
    if ($request->hasFile('foto') && !$request->file('foto')->isValid()) {
        return back()->withErrors(['foto' => 'El archivo de foto no pudo subirse. Intenta con una imagen más pequeña (máx. 4MB).']);
    }

CAUSA D: El formulario se re-envía (solicitado_aprobacion_at actualiza)
------------------------------------------------------------------------
En el controller, línea 163:
    $data['solicitado_aprobacion_at'] = now();

Y línea 167-170: si el proveedor ya estaba aprobado, lo desaprueba:
    if ($restaurantero->aprobado) {
        $data['aprobado'] = false;
        $data['activo']   = false;
    }

Esto es correcto. Pero si el proveedor edita perfil repetidamente,
pierde la aprobación cada vez. Considerar: solo resetear si cambió
información sustancial. Por ahora se deja igual pero hay que documentarlo.

CAUSA E: Agregar logging para debug
------------------------------------
Para identificar el problema en producción, agregar logging temporal
al inicio del método store():

    \Log::info('ProveedorPerfil::store inicio', [
        'user_id' => $request->user()->id,
        'has_foto' => $request->hasFile('foto'),
        'entrega_domicilio' => $request->input('entrega_domicilio'),
        'sitio_web' => $request->input('sitio_web'),
    ]);

Y al final:
    \Log::info('ProveedorPerfil::store OK', ['restaurantero_id' => $restaurantero->id]);

Así en production.log se podrá ver si la petición llega pero falla en
validación (no aparecerá el log "OK") o si hay otro problema.
