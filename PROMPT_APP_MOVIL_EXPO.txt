─────────────────────────────────────────────────────────────
1.3 — Las nueve reglas que separan una app bonita de una fea
─────────────────────────────────────────────────────────────

Pedías que se viera hermosa. Estas son las decisiones concretas que lo logran.
Aplícalas en TODAS las pantallas, no solo en la primera.

**1. Respeta el notch y la barra de gestos.**
   Envuelve todo en `SafeAreaView` de `react-native-safe-area-context` (NO el
   de react-native, que está obsoleto). Contenido pegado al borde superior es
   la señal más rápida de "esto es una web metida en una app".

**2. Zona táctil mínima de 44×44.**
   Un icono de 20px necesita `hitSlop={{top:12,bottom:12,left:12,right:12}}`.
   Botones con `paddingVertical: 14` como piso.

**3. Esqueletos, no ruedas girando.**
   Mientras carga, muestra cajas grises con la forma del contenido que va a
   llegar, animadas con un pulso suave. Se percibe hasta un 30% más rápido que
   un spinner, porque el ojo ya sabe qué esperar.

   Crea `components/Skeleton.tsx` con `Animated.View` y un loop de opacidad
   entre 0.4 y 0.8.

**4. Entrada escalonada de las listas.**
   Con reanimated, cada tarjeta entra con un retraso de 60 ms sobre la
   anterior:

       import Animated, { FadeInDown } from 'react-native-reanimated';
       <Animated.View entering={FadeInDown.delay(indice * 60).duration(320)}>

   Es sutil y cambia por completo la sensación de calidad.

**5. Vibración en las acciones que importan.**

       import * as Haptics from 'expo-haptics';
       Haptics.impactAsync(Haptics.ImpactFeedbackStyle.Light);   // al tocar
       Haptics.notificationAsync(Haptics.NotificationFeedbackType.Success); // al confirmar

   Úsalo al confirmar un registro, al agendar una cita, al hacer check-in.
   NO en cada toque: pierde sentido.

**6. Estados vacíos con propósito.**
   Nunca una pantalla en blanco. Un icono grande y suave, una frase que
   explique qué pasa, y un botón con la acción siguiente.
   Mal: "No hay datos". Bien: "Todavía no tienes citas agendadas" + botón
   "Explorar proveedores".

**7. Botones con tres estados visibles.**
   Normal, presionado (`Pressable` con `opacity: 0.85` o escala 0.97), y
   cargando (spinner dentro del botón, texto que cambia, botón deshabilitado).
   Un botón que no reacciona al tocarlo se siente roto — es justo el problema
   que ya tienes reportado en la web.

**8. Jerarquía por peso, no por tamaño.**
   Tres tamaños de texto bastan. La jerarquía la dan el grosor de la fuente y
   el color: `neutral.900` para lo importante, `neutral.500` para lo
   secundario, `neutral.400` para lo terciario.

**9. Modo oscuro desde el principio.**
   El sitio web ya lo tiene, así que los usuarios lo esperarán. Usa
   `useColorScheme()` y define los colores como pares claro/oscuro en el tema.
   Añadirlo después obliga a repasar todas las pantallas.

  Citas agrupadas por día, con encabezados pegajosos (`SectionList` con

  proveedor y estado a la derecha, borde izquierdo de color según el estado.
  Estado vacío con botón a Proveedores.

⚠⚠ 2.1 — EL ERROR QUE HAY QUE EVITAR
=====================================

La tentación es escribir controladores de API que repitan la lógica de los
web. **No lo hagas.**

El proyecto YA sufre esto: la reserva de citas está copiada en tres sitios
con **cuatro fórmulas distintas de duración**:

    CitaPublicaController:136-171       → duración del evento
    CitaAdminController:110-143         → duración del request
    RestauranteroCitasController:118    → duración del servicio, sin transacción

Ya divergieron. Una cuarta copia en la API significa que, el día del evento,
tendrás citas con reglas distintas según desde dónde se agendaron.

**Antes de exponer nada, extrae la lógica a servicios:**

  `app/Services/RegistroEventoService.php`
      registrarComprador / registrarProveedor / registrarExpositor
      Mueve aquí lo de `EventoRegistroController`. Que lance una
      `ReglaDeNegocioException` propia, no `ValidationException` (que es HTTP).

  `app/Services/AgendaCitaService.php`
      agendar(comprador, proveedor, evento, inicio, duracion?, opciones?)
      UNA sola regla de duración, el cupo excluyendo canceladas, el colchón
      de 10 minutos **a ambos lados** (hoy solo se aplica al comprador),
      `DB::transaction` + `lockForUpdate`.
      Llámalo desde los tres sitios que hoy tienen su copia.

      ⚠ `confirmarToken` hoy reescribe horarios sin transacción ni
         comprobación de solapes. Al pasar por el servicio, ese agujero se
         cierra solo.

Después, los controladores web deben quedar en ~15 líneas por método, y el
comportamiento del sitio debe ser EXACTAMENTE el mismo. Si algo cambia, es un
error de la extracción.


2.2 — Estructura

  • Todo bajo `/api/v1`. Sin excepciones: cuando la app esté en una tienda,
    habrá usuarios con versiones viejas durante meses.
  • NO toques las 6 rutas existentes: `/api/notificaciones` la usa el web con
    polling cada 30 segundos.
  • Controladores en `app/Http/Controllers/Api/V1/`.
  • API Resources en `app/Http/Resources/`. No es burocracia: el proyecto ya
    tuvo una fuga por serializar de más (`ine_path` y `csf_path` viajaban al
    frontend sin necesidad). El Resource es el único sitio donde decides qué
    sale, y se revisa de un vistazo.

    En `UserResource`, NUNCA: `ine_path`, `csf_path`, `password`,
    `remember_token`, `two_factor_*`. Para documentos, booleanos
    (`tiene_ine`, `tiene_csf`) y URL firmada temporal si hay que verlos.

  • Forma de las respuestas, siempre igual:

        { "data": {...}, "message": "opcional" }
        { "data": [...], "meta": { "current_page":1, "last_page":4 } }
        { "message": "...", "errors": { "campo": ["..."] } }


2.3 — Autenticación

`app/Http/Controllers/Api/V1/AuthController.php`:

    POST /api/v1/auth/login          email, password, device_name
                                     → { token, user, onboarding }
                                     throttle:5,1
    POST /api/v1/auth/logout         (auth:sanctum)
    GET  /api/v1/auth/me             (auth:sanctum)
    POST /api/v1/auth/logout-todos   cierra sesión en todos los dispositivos

⚠ LAS RUTAS DE API NO DEBEN PASAR por `EnsureAvisoAceptado`,
   `EnsureRolSeleccionado` ni `EnsureProfileComplete`. Esos middlewares
   devuelven **redirecciones HTTP**, que en una app nativa no significan nada.
   Comprueba en `bootstrap/app.php` que estén solo en el grupo `web`.

   En su lugar, el login devuelve el estado como DATO y la app decide:

       "onboarding": {
         "aviso_aceptado": true, "rol_seleccionado": true,
         "perfil_completo": false,
         "siguiente_paso": "completar_perfil",
         "rol_activo": "comprador"
       }

   `siguiente_paso` ∈ aceptar_aviso | seleccionar_rol | completar_perfil | ninguno.
   Que lo decida el servidor evita que la app reimplemente el orden mal.

⚠ Caducidad: `config/sanctum.php` tiene `'expiration' => null` (los tokens no
   caducan nunca). Para teléfonos que se pierden, pon `60 * 24 * 30`.


2.4 — Primer corte vertical

No construyas 60 endpoints de golpe. Haz UNO completo y el resto se vuelve
mecánico:

    GET  /v1/eventos
    GET  /v1/eventos/{evento}
    POST /v1/eventos/{evento}/registro     body: { tipo }

`EventoResource` debe incluir lo que la app necesita para pintar la tarjeta,
**con las decisiones ya tomadas por el servidor**:

    mi_registro: { comprador: 'pendiente'|null, proveedor: ..., expositor: ... },
    puede_registrarse: true|false,
    motivo_bloqueo: "El registro de compradores abre el 25 de agosto"

⚠ Si la app deduce `puede_registrarse` por su cuenta, tendrás dos versiones
   de las reglas de ventanas — el mismo problema de las cuatro duraciones,
   pero ahora entre dos lenguajes.


2.5 — Seguridad

  • **Policies.** La auditoría lleva tres rondas señalando que el proyecto
    tiene cero Policies. En la web lo tapan los middlewares de rol; una API
    sin Policies es mucho peor. Créalas ANTES de exponer endpoints con
    `{cita}`, `{user}` o `{evento}`.
  • **CORS.** En `config/cors.php`, NO uses `allowed_origins: ['*']` junto con
    `supports_credentials: true`. Con tokens Bearer no necesitas credenciales:
    déjalo en `false` y lista los orígenes.
  • **Rate limit por token**, no solo por IP.
  • **Subida de archivos**: una foto de teléfono pesa 4–12 MB. Aplican los
    límites de PHP que ya tienes pendientes de revisar (`upload_max_filesize`,
    `post_max_size`). Si la app sube fotos, es requisito.

3.1 — ⚠ EL PROBLEMA DE `localhost` CON EXPO GO

El teléfono NO comparte `localhost` con tu computadora. `http://localhost/citas`
desde la app apunta al propio teléfono y falla siempre. Tres salidas:

**OPCIÓN A (la más simple para empezar) — apunta a producción**

    const API_URL = 'https://impulsate.iyemyucatan.com/api/v1';

    Ventaja: HTTPS real, sin configurar nada, funciona desde cualquier red.
    Desventaja: pruebas contra datos reales. Crea usuarios de prueba.

**OPCIÓN B — tu XAMPP por IP de la red local**

    1. En Windows: `ipconfig` → anota la IPv4 (ej. 192.168.1.50)
    2. API_URL = 'http://192.168.1.50/citas/api/v1'
    3. XAMPP debe escuchar en la red, no solo en 127.0.0.1
    4. Abre el puerto 80 en el Firewall de Windows para Apache
    5. Teléfono y PC en la MISMA Wi-Fi

    ⚠ Android bloquea HTTP sin cifrar. En Expo Go de desarrollo funciona,
       pero si luego haces un build necesitarás `usesCleartextTraffic` en
       `app.json` — o mejor, HTTPS.

**OPCIÓN C — túnel a tu XAMPP**

    npx localtunnel --port 80      (o ngrok)

    Te da una URL HTTPS pública hacia tu máquina. Útil para probar desde
    fuera de la oficina.

⚠ Pon la URL en `app.json` bajo `extra`, y léela con `expo-constants`. No la
   escribas a mano en cada archivo: cambiarás de entorno muchas veces.


3.2 — El cliente HTTP

`lib/api.ts` — UN solo cliente axios, con interceptores. Nada de `fetch`
suelto por las pantallas:

import axios from 'axios';
import * as SecureStore from 'expo-secure-store';
import Constants from 'expo-constants';

export const api = axios.create({
  baseURL: Constants.expoConfig?.extra?.apiUrl,
  timeout: 15000,
  headers: { Accept: 'application/json' },
});

api.interceptors.request.use(async (config) => {
  const token = await SecureStore.getItemAsync('token');
  if (token) config.headers.Authorization = `Bearer ${token}`;
  return config;
});

api.interceptors.response.use(
  (r) => r,
  async (error) => {
    if (error.response?.status === 401) {
      await SecureStore.deleteItemAsync('token');
      // redirigir al login
    }
    return Promise.reject(error);
  }
);

⚠ El token va en `expo-secure-store` (llavero del sistema), NUNCA en
   AsyncStorage, que es texto plano legible en un teléfono con root.

⚠ El header `Accept: application/json` no es opcional: sin él, Laravel puede
   responder con redirecciones HTML en vez de errores JSON.


3.3 — Estado del servidor con React Query

Envuelve la app en `QueryClientProvider` en `app/_layout.tsx`. Después, cada
pantalla usa `useQuery` y `useMutation`. Te da caché, reintentos,
pull-to-refresh y estados de carga sin escribirlos a mano.

Sustituye los `datos-simulados/` pantalla por pantalla, no de golpe: así
siempre tienes algo funcionando.


3.4 — La app NO reimplementa reglas de negocio

Si necesita saber si alguien puede registrarse, lo pregunta a la API
(`puede_registrarse`, `motivo_bloqueo`). En cuanto empieces a copiar lógica a
React Native, tendrás el problema de las cuatro duraciones entre dos
lenguajes distintos.

PARTE 1 — la app en Expo Go
  □ Abre en Expo Go sin errores de versión de módulos
  □ Las fuentes Figtree cargan (si no, el texto se ve con la fuente del sistema)
  □ El contenido respeta el notch y la barra inferior
  □ Las pestañas cambian de color al seleccionarse
  □ Las listas entran escalonadas, no de golpe
  □ Los esqueletos aparecen mientras "carga"
  □ Los botones reaccionan al presionarlos
  □ Los estados vacíos tienen icono, texto y acción
  □ Se ve bien en un teléfono pequeño y en uno grande
  □ El modo oscuro no deja texto ilegible

PARTE 2 — la API
  □ Registrarse a un evento DESDE LA WEB sigue funcionando igual que antes
  □ Agendar una cita desde el directorio sigue funcionando igual
  □ La duración de la cita es la misma por los tres caminos
  □ POST /api/v1/auth/login devuelve token
  □ Sin token, la API devuelve 401 en JSON, NO una redirección HTML
  □ Seis intentos de login seguidos devuelven 429
  □ Ningún endpoint devuelve `ine_path` ni `csf_path`
  □ Un usuario no puede leer datos de otro cambiando el id de la URL

PARTE 3 — conexión
  □ La app alcanza la API desde el teléfono
  □ El login guarda el token en SecureStore
  □ Cerrar y reabrir la app mantiene la sesión
  □ Un 401 devuelve al login automáticamente
  □ El registro hecho desde la app aparece en el panel de admin
  □ Sin conexión, la app muestra un mensaje claro y no se queda colgada
